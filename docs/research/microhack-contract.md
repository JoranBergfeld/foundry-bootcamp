# MicroHack lab and environment contract: evidence for Winter Bootcamp

Research resolution for [ticket #2](https://github.com/JoranBergfeld/foundry-bootcamp/issues/2), supporting [wayfinder map #1](https://github.com/JoranBergfeld/foundry-bootcamp/issues/1).

## Scope and answer

Investigated on 24 November 2026 against public Microsoft-owned MicroHack repository sources at **`2d3ab57256c930718b48df419ac051cfac24a317`**. The [commit API][revision] identifies this as the `main` revision retrieved during this investigation, committed at `2026-11-24T16:36:51Z`. MicroHack links below pin that revision; they are not claims about future `main`. Additional user-provided advanced-RAG source evidence is separately pinned and attributed in section 4.

**There is an explicit, conditional platform provisioning contract, but no universal requirement that six learning sessions receive six environments or credential sets.** The repository README delegates prerequisites to each workshop. The master template's `labautomation/README.md` documents concrete platform configuration, hook signatures, RBAC, credential publication, import packaging and cleanup. Automation is optional; those integration requirements apply when using it, not to every hands-on exercise regardless of hosting. Workshop examples reuse one environment across successive challenges, but do not specify how six separately imported content packs retain one participant identity/environment for a day. [S1][root] [S2][contributing] [S4][automation]

This report gathers evidence only. It does **not** select the bootcamp directory tree, infrastructure, identity model, import arrangement, reset policy, or lab implementation.

### Classification

- **Repository guidance:** explicit authoring instructions in root contribution documentation. Requirements for contributing upstream are not automatically requirements for this downstream repository.
- **Conditional platform contract:** explicit documented rules for content imported into the MicroHack platform or its optional automation.
- **Workshop requirement/example:** necessary within that workshop, or a demonstrated convention; not a repository-wide mandate.
- **Gap/inconsistency:** not established by the inspected sources, or conflicting source instructions requiring confirmation.

## 2. Explicit platform contract: not merely one workshop's example

The owning public documentation is **`99-MicroHack-Template/labautomation/README.md`**, corroborated for configuration shape by the root **`lab-defaults-schema.json`** and for the per-participant signature by the template script. These are stronger evidence than inferring a platform contract from Fraud or Governance alone. The actual hosted platform implementation was not inspected or exercised. [S4][automation] [S6][schema] [S22][template-script]

### Configuration and provisioning

- `labautomation/` is **optional** and can be deleted when automated Azure provisioning is unnecessary. When present, its configuration file `lab-defaults.json` is required; configuration is validated on import. `deploy-lab.ps1` and `shared-deploy-lab.ps1` are optional and discovered by filename. A missing or signature-mismatched per-participant script leaves an empty provisioned scope plus RBAC, with a warning for mismatch. [S4][automation]
- Documented per-user scopes are: `resourcegroup` = shared subscription, subscription Reader and RG Owner; `resourcegroup-with-subscriptionowner` = shared subscription, subscription Owner and RG Owner; `subscription` = dedicated subscription and subscription Owner, with **no pre-created RG**. `labsPerSubscription` ranges from 1–100; regional preferences, per-environment/shared/event daily cost estimates and optional capability groups are configurable. These are choices, not a universal RG-only rule. [S4][automation] [S6][schema]
- The per-participant parameter contract is `DeploymentType` (mandatory string; three modes), `SubscriptionId` (mandatory string), `ResourceGroupName` (string, empty in subscription mode), `PreferredLocation` (string array, or documented comma-separated string alternative), and `AllowedEntraUserIds` (string array). The platform fans out **one identical script per participant**, in separate processes. Scripts must grant additional resource/data-plane access to the intended IDs, not assume RG Owner grants every service's data-plane access. [S4][automation] [S22][template-script]
- Before a platform script runs, documentation guarantees Az/CLI authentication and subscription context, isolated CLI profiles, imported helper cmdlets, and provisioner service-principal subscription Owner. Scripts must **not** call `Connect-AzAccount`, `Set-AzContext` or `az login`. This is the **provisioner** contract; participant guides separately require participant CLI sign-in. It does not mean attendees receive the service-principal identity. [S4][automation] [S14][claims-setup]
- Scripts should converge on a working lab on rerun, retain stable unique names, honor ordered preferred regions with warnings/errors rather than silently hardcoding, and avoid concurrent global state. Bicep/ARM region-fallback helpers are preferred. OpenTofu is supported but not recommended: job-local state does not survive rescheduling; direct `tofu` invocation and a shared backend are forbidden by the documented integration rules. Long commands retain their original token; the approximately 90-minute guidance and refresh helpers concern provisioning jobs, **not a participant account's six-hour lifetime**. [S4][automation]

### Meaning of “shared” and “lab”

- `shared-deploy-lab.ps1` runs **once per subscription before per-participant deployments**. Its contract takes subscription, preferred locations and **all participant IDs in that subscription**, but no participant RG. Shared resources belong in its own RG, with explicit grants to all intended users; shared outputs fan out to every participant in that subscription. It also covers one-time provider registration. It is not a documented hook “once per teaching session.” [S4][automation]
- An opt-in `global-event-deploy.ps1` runs **once per event**, before shared hooks, in the lowest-GUID event subscription; it receives all event participant IDs. It needs the documented signature, `estimatedGlobalDeploymentDailyCostsUsd > 5`, and content re-import. Its outputs reach all event users, so organizer-only credentials must not be emitted. [S4][automation] [S6][schema]
- “No cross-lab state” in the platform guide refers to **parallel copies for different participants**, including CLI/OpenTofu process state. The same guide expressly allows shared subscription/event resources via hooks. It does **not** prohibit successive challenges for one participant from using one environment, nor establish cross-content-pack reuse. [S4][automation]
- Shared-hook documentation's explicit failure table/callout says one subscription's failing shared hook blocks **all participants in the event**. Governance's README describes the failure as stopping that subscription's labs. Treat the platform guide's global gate as the documented contract, but confirm the deployed host version before relying on failure isolation. [S4][automation] [S20][governance-automation]

### Credentials, content distribution and cleanup

- `HackboxCredential` output must be separate hashtables with nonempty `name`/`value`; `note` is optional. A `PSCustomObject` is ignored. Re-emitting a name overwrites it; reserved names are silently dropped. Publish values only after successful application. Generated passwords use `New-MhhStablePassword` for stable per-lab/per-purpose reruns. This channel includes endpoints, resource names and configuration, **not only passwords**. [S4][automation]
- The template documents console `<secret ... />` rendering in challenge/solution Markdown. It is platform behavior, not standard GitHub Markdown secret substitution. [S3][template] [S4][automation]
- Imported content has a student side without `walkthrough/` and coach side without `challenges/`; **`labautomation/` appears on neither side**. Shared top-level entries appear on both published sides. Download ZIPs additionally omit the respective challenge/solution Markdown and top-level entries such as `Readme.md`. Paths/removals/renames are exact and case-sensitive; renaming does not rewrite links. These rules matter when executable code is only under `walkthrough/`, or participant instructions invoke scripts in `labautomation/`: GitHub checkout and platform-distributed artifacts cannot be assumed equivalent. [S4][automation] [S6][schema]
- Normally the platform deletes participant scope when the event ends. Explicit retry teardown should use `Remove-MhhResourceGroup` to handle backup/soft-delete residuals, restore RG Owner grants after recreation, and clear OpenTofu workspace when appropriate. A rerun/fallback can be destructive; “idempotent provisioning” is **not a guarantee that participant-generated agent/index/data state survives it**. [S4][automation]

## 4. Provided Build it (advanced) source: separate from MicroHack

The user identified **https://github.com/syash-git/foundryIQ-rag-workshop** as the received source for **Build it (advanced)** during this investigation. It is **not** `microsoft/MicroHack`; its workshop requirements must not be attributed to MicroHack or treated as adoption of its provisioning. Bounded public read: README, Module 1 setup/ingestion pointers, Module 3 connection/agent pointers, and repository tree. The public `main` revision retrieved was **`973494c76e780199c5075b010a58fd1931cd480b`**. [A1][rag-readme] [A2][rag-source] [A3][rag-agent] [A4][rag-tree]

- **Existing resources, not an infrastructure deployment package.** Its README explicitly says setup commands provision no Azure resources and asks an administrator to pre-provision/assign roles when necessary. Module 1 says its script creates no storage account, container, model deployment or Search service. Prerequisites include a non-hub Foundry project, compatible chat/embedding deployments, agentic-retrieval-capable Search, Blob Storage with approved documents, appropriate networking and Python/CLI. This is a requirements inventory relevant to shared provisioning, not a reason to provision a second bootcamp environment. The inspected tree has no `labautomation/`, `infra/` or `azure.yaml` deployment entry point. [A1][rag-readme] [A2][rag-source] [A4][rag-tree]
- **Identity and credential distinctions.** README describes `DefaultAzureCredential` for local clients, participant Search and Foundry/connection-management roles, Search managed-identity model access, and Foundry-project managed-identity Search reader access. Blob reads currently use a **storage connection string**, separate from CLI login; an MI alternative needs Search-identity Blob Data Reader. These author-documented prerequisites are not a universal MicroHack identity contract. It explicitly warns that `env.example` contains a populated connection string: that file was **not read, copied or imported**. Do not republish it; authorized owners should replace/rotate an exposed key if valid. No secret value is recorded here. [A1][rag-readme] [A2][rag-source]
- **State continuity and cleanup.** Modules use the same process environment and component names. Module 1 uses create/update semantics; Module 3 warns agent creation can add versions and rerunning the original script does not preserve portal-only retrieval-tool/instruction changes. Its cleanup order is agent versions/project connection, then knowledge base, then referenced knowledge source; source blobs remain. Dedicated services/RG may be removed only after confirming nothing is shared. Applied unchanged between bootcamp sessions, that teardown could destroy state needed later; timing/ownership must remain a later decision. [A1][rag-readme] [A2][rag-source] [A3][rag-agent]
- **Bounded compatibility gaps, not a runnable-source endorsement.** Module 3 says the starting agent has **no retrieval tool** and needs knowledge-base connection/attachment plus authorized project MI; instructions alone are insufficient. Module 1 notes no per-folder ingestion filter, and Module 3 says no per-user document-permission ingestion/filtering. Module 3 calls the local web-app module deferred, while README advertises it. README/module links reference root Python scripts, but the pinned tree places the listed executables under `src/` and lacks some referenced root names. Therefore this read does not verify an out-of-box executable advanced lab, advanced-RAG acceptance scope, dependency/API compatibility or one-hour duration. Do not resolve those gaps by importing code or deciding architecture in this ticket. [A1][rag-readme] [A2][rag-source] [A3][rag-agent] [A4][rag-tree]

## 5. Conflicts, gaps and implications for the agreed bootcamp

The fixed sequence remains **Build it (basic); Build it (advanced, including advanced RAG); Evaluate it; Deploy it; Integrate it; Govern it**. Each lab owns executable code and participant docs, provisioning is shared, and one participant retains one environment for the day. The evidence yields constraints to clarify later, not decisions:

1. **Compatible in principle, not an established cross-pack guarantee.** CLM, Claims, Inventory and Fraud all show later challenges consuming earlier work in the same environment; CLM explicitly keeps one Foundry project. No inspected contract requires a new human account per challenge. However, the platform's “lab” is a participant deployment/dashboard unit, not necessarily this bootcamp's one-hour learning unit. No inspected source documents binding six independent imported MicroHacks to one identity/scope/dashboard, preserving a Codespace between them, or orchestrating a six-participant-guide provisioning interface. Do not silently equate those meanings. [S4][automation] [S7][inventory] [S9][clm] [S13][claims] [S17][fraud]
2. **Avoid six credential sets is not the same as zero service secrets.** Inventory demonstrates one lab identity with keyless Cosmos. Claims retrieves multiple API secrets into one local file. CLM/M365 and Governance/MCP may require tenant applications, consent, sideload permissions and access-contract credentials. General optional groups document licenses, not a universal Azure/GitHub/M365 account federation/consent contract. Exact credential delivery, token renewal, role expansion and isolation remain unspecified for the bootcamp. [S6][schema] [S8][inventory-automation] [S10][clm-setup] [S15][claims-key-script] [S18][governance]
3. **Least privilege and lifecycle are not uniform.** Inventory/CLM/Governance default to RG Owner plus subscription Reader; Claims/Fraud use subscription Owner in a shared subscription. Shared provider registration avoids granting every participant registration rights in Governance. Select no universal permission contract from these defaults. Account expiry time, renewal during the day, cleanup timing of shared/global resources, tenant-app/license/GitHub/Codespace cleanup, and retention of evaluation/tracing artifacts are not fully established by this evidence. The platform guide's event-end scope deletion is not a complete all-resource teardown specification. [S4][automation] [S16][claims-defaults] [S20][governance-automation] [S25][inventory-defaults] [S26][clm-defaults] [S28][fraud-defaults]
4. **Code distribution must be distinguished from code ownership.** No root mandate fixes executable code to `src/`, `docs/` or walkthroughs. The bootcamp's per-lab ownership is an agreed local constraint; several layouts illustrate it differently. The platform distribution split can hide walkthrough code or automation setup helpers from attendees. Claims asks participants to run `labautomation/get-keys.sh`, while the generic import guide excludes `labautomation/`; Fraud uses walkthrough scripts while the student side excludes `walkthrough/`. Both describe GitHub checkout workflows, but that is not proof those scripts arrive in Student ZIPs. Later specification must account for the actual participant delivery path. [S4][automation] [S14][claims-setup] [S27][fraud-setup]
5. **Recovery is not a reset contract.** CLM's coach guide distinguishes repairing `.env`, reseeding, waiting for RBAC and full `azd down`/redeploy. Its full reset destroys the shared project state. Governance's finish says deleting/purging permits redeploy, whereas its automation notes describe Foundry hidden soft-delete backing state that may still require fresh account names. These are local recovery observations, not proof of a universal safe reset between sessions. No inspected source defines per-bootcamp-lab entry/exit artifacts, skip-ahead recovery, or selective reset preserving earlier lab work. [S4][automation] [S20][governance-automation] [S21][governance-finish] [S29][clm-coach]
6. **Conflicting docs must not become mandates.** CLM's root/setup docs call local-PDF grounding the default with SharePoint optional; its automation/coach docs still call per-participant admin-tenant SharePoint the default. Its coach notes assume sandbox tenant admin, which is not promised by the general Azure RBAC contract. Governance documents both optional `.env` and `azd` bridges; they are alternatives, not two identities. Root lowercase/`iac/` guidance differs from checked-in AI examples. Template script's example first-region fallback is less strict than its automation guide's region-validation guidance. None justifies silently choosing a bootcamp architecture. [S2][contributing] [S4][automation] [S10][clm-setup] [S12][clm-automation] [S18][governance] [S22][template-script] [S29][clm-coach]
7. **One-hour feasibility is not verified.** Setup, quotas/model availability, asynchronous RBAC and notebook/container deployments consume time. CLM evaluation has actual prerequisites, not a standalone stateless exercise. Existing topic coverage demonstrates relevant patterns, not executable acceptance of this exact six-hour sequence, advanced-RAG objective, state handoffs or dependency compatibility. Those checks belong to later specification and implementation work. [S7][inventory] [S9][clm] [S11][clm-eval] [S20][governance-automation]

Did not deploy Azure resources, invoke provisioners, execute external scripts, inspect live credentials, or validate hosted platform behavior.

- Public sources meaningfully answer ticket #2. The unresolved cross-content-pack identity/state/lifecycle arrangement is a documented evidence gap, not a blocker to closing this research ticket. Structural choices stay on the planning map for later decision/specification work.
